2. Design of the task systems

All three parallel task systems assign task ids dynamically, in increasing order: a free worker claims the next unclaimed id from a shared counter. A task is counted as finished only after runTask() returns, never when it is claimed. The calling thread does not execute tasks; it only waits.

2.1 Spawn (Part 1) — TaskSystemParallelSpawn::run

std::atomic<int> next_task(0);
auto worker = [&]() {
    for (int id = next_task++; id < num_total_tasks; id = next_task++)
        runnable->runTask(id, num_total_tasks);
};
// min(num_threads, num_total_tasks) threads run worker(); the caller joins all of them.

Shared scheduler state.

  • The next-task counter. Every worker read-modify-writes it, so it is a std::atomic<int>. fetch_add returns each value exactly once, so every id in [0, n) goes to exactly one worker.
  • runnable and num_total_tasks. Shared, but read-only during the launch. Creating a thread makes them visible to it.
  • Task outputs. Written by the tasks and made visible to the caller by join(). That is also what makes run() synchronous: it returns only after every worker has run out of ids and exited.

No more than num_threads threads are ever created, and none is created that would find no task.

2.2 Spinning pool (Part 2) — TaskSystemParallelThreadPoolSpinning

The constructor starts num_threads workers that live until the destructor sets shutdown_ and joins them. mutex_ guards the current launch (runnable_, num_total_tasks_, next_task_). tasks_done_, has_work_ and shutdown_ are atomics.

while (!shutdown_) {                                // worker loop
    if (!has_work_) continue;                       // idle: spin on an atomic load
    std::unique_lock<std::mutex> lock(mutex_);
    if (next_task_ >= num_total_tasks_) continue;   // lost the race for the last task
    int task_id = next_task_++;
    if (next_task_ == num_total_tasks_) has_work_ = false;
    /* copy runnable_ and num_total_tasks_, unlock, run the task */
    tasks_done_++;                                  // counted after the task finished
}
// run(): publish the launch under mutex_ (reset counters, has_work_ = n > 0),
//        then spin: while (tasks_done_ < n) {}

Idle workers spin on a plain atomic load (has_work_) and take the mutex only when a task is probably available. A spin built from repeated lock/unlock would make idle workers fight working ones for the mutex. The design stays correct across consecutive launches for two reasons:

  1. Every increment of tasks_done_ for launch k happens before run(k) returns, so the reset in run(k+1) cannot drop or misattribute an increment.
  2. Claims happen under the same mutex that publishes a launch, so a worker can never pair a task id of launch k+1 with the runnable of launch k.

2.3 Sleeping pool (Part 3) — TaskSystemParallelThreadPoolSleeping

std::unique_lock<std::mutex> lock(mutex_);       // worker loop
while (true) {
    work_cv_.wait(lock, [this] { return shutdown_ || next_task_ < num_total_tasks_; });
    if (shutdown_) return;
    int task_id = next_task_++;
    /* copy runnable_ and num_total_tasks_ */
    lock.unlock();  runnable->runTask(task_id, num_total_tasks);  lock.lock();
    if (++tasks_done_ == num_total_tasks_) done_cv_.notify_one();   // last task wakes run()
}
// run(): lock; publish the launch; work_cv_.notify_all();
//        done_cv_.wait(lock, [this] { return tasks_done_ == num_total_tasks_; });

All state is guarded by one mutex. After finishing a task, a worker keeps the lock to record the completion and claim its next task, so each task costs one lock round trip. The destructor sets shutdown_ under the lock, calls notify_all() and joins. No thread busy-waits anywhere.

3. Part 1 — Synchronous parallel launch with Spawn

3.1 Correctness and the added test

The added test is exactly_once_stress in tests/tests.h, registered in tests/main.cpp. It makes 20 rounds of back-to-back launches with task counts 0, 1, 2, 3, 5, 7, 8, 9, 15, 16, 17, 31, 33, 63, 64, 65, 127, 1000 and 4099. That covers very few tasks, many tasks, and counts that are not divisible by any power-of-two worker count. Each task busy-waits for a task-dependent 0–2 µs, so tasks finish out of order, then atomically increments a counter for its id. Right after each run() returns, every counter must be exactly 1. The test fails if any task ran twice (a duplicate claim), never ran, or had not finished when run() returned.

It passes for all implementations at p = 1, 2, 3, 5, 8, 16 and 32, including 30 repeated runs. All supplied tests pass too (Appendix B), and ThreadSanitizer reports no races.

3.2 Predictions recorded before measuring

  • Best scaling: recursive_fibonacci. It is compute-bound with no memory traffic, has 256 identical tasks per launch (far more than p), and only 30 launches, so launch overhead is negligible. I expected S ≈ 7 at p = 8 and 10–30% more at p = 16 from SMT.
  • Worst scaling: super_super_light. A task copies 512 ints (about 0.5 µs) and there are 400 launches, so creating and joining threads in every launch should cost more than the work. I expected Spawn to be slower than serial at every p.
  • Non-uniform workload (ping_pong_unequal): dynamic assignment of 64 tasks should absorb the cost skew, and memory traffic should limit scaling at p = 4–8.

3.3 Measurements (Spawn)

The three chosen workloads are super_super_light (very small tasks), recursive_fibonacci (substantial work per task) and ping_pong_unequal (non-uniform task cost). Appendix A has every workload and implementation.

3.4 Analysis

First worker count where adding workers gains less than 10%.

  • super_super_light: p = 2. Doubling to 2 gains only 5% (27.8 → 26.3 ms), and every further doubling makes it slower: 32.2, 77.3 and 178.1 ms. The extra time is almost exactly the cost of creating more threads. Spawn exceeds the spinning pool by 55 µs per launch at p = 4 and 161 µs at p = 8, i.e. about 14–20 µs per thread created and joined, while one launch contains only about 31 µs of work (12.3 ms / 400).
  • recursive_fibonacci: p = 16. From 1 to 8 every doubling gains 48–50% (S8 = 7.61). From 8 to 16 it gains 0.4%. p = 16 adds no cores, only SMT siblings, and this recursive call/branch-heavy code already keeps a core's execution resources busy, so two threads per core just share them.
  • ping_pong_unequal: p = 16. It gains 45–50% per doubling up to 8 (S8 = 6.76), then −0.9% from 8 to 16, for the same SMT reason. Each launch also streams the 2 MB input and output arrays through the shared L3, which the siblings share as well.

Static vs dynamic assignment for the irregular workload. In ping_pong_unequal, element i costs about 2·iters·(1 − i/N), so task t of 64 costs about 2(1 − (t+0.5)/64) times the average: task 0 about 2×, task 63 about 0.02×.

  • Load balance. A static contiguous split gives worker 0 of 4 tasks 0–15, which is 44% of the work, so the makespan is 1.75× ideal (57% efficiency). A static interleaved split (t mod p) is much better: the worst worker gets 16.75/16 of its share, about 95% efficiency. Dynamic assignment is better still. Tasks are claimed in decreasing cost order, so the only imbalance is the final cheap tasks, and the work comes out nearly perfectly balanced.
  • Scheduling cost. Static assignment needs no coordination: a worker computes its own ids. Dynamic assignment costs one atomic fetch_add per task, roughly 50–100 ns when the cache line moves between cores, so 64 × 100 ns ≈ 6 µs per launch. Each launch here does 2.2 ms of work at p = 4, so the cost is negligible.

Dynamic assignment is therefore expected to balance this workload better at negligible cost. That matches the measurement: Spawn reaches E4 = 0.93 and E8 = 0.85 on ping_pong_unequal, the same as on ping_pong_equal. The Part 4 example measures the difference directly: the static split takes 20.15 ms and the dynamic one 11.13 ms (Section 6). Dynamic assignment loses only when tasks are so small that the per-task claim is comparable to the task itself (Section 6.3).

A correct run with little or no speedup. super_super_light under Spawn produces correct results but Sp = 0.44, 0.47, 0.38, 0.16 and 0.07 for p = 1 to 16. At p = 16 it takes 178 ms against 12.3 ms serially. A launch holds about 31 µs of useful work but Spawn creates and joins up to 16 threads per launch at about 20 µs each, so the program spends more than 90% of its time on thread management. A second example is spin_between_run_calls, where Sp stays at 1.99 for every p ≥ 2: the only heavy launch has 2 tasks, so at most 2 workers are ever useful.

4. Part 2 — Persistent thread pool with spinning

Fine- vs coarse-grained workloads. Replacing per-launch thread creation with a persistent pool helps exactly where launches are short.

  • Fine-grained. At p = 8, super_light drops from 83.7 ms (Spawn) to 21.9 ms (Spin), 3.8× faster. math_operations_in_tight_for_loop drops from 472.8 to 246.9 ms (1.9×), and super_super_light at p = 4 from 32.2 to 10.2 ms.
  • Coarse-grained. Nothing changes: recursive_fibonacci 210.8 vs 215.3 ms, mandelbrot_chunked 94.9 vs 95.9 ms.

The reason is that thread creation is a fixed cost per launch, about 15–20 µs per thread. Compare it with the work in one launch:

  • recursive_fibonacci: about 53 ms per launch (1605 ms / 30), so the overhead is under 0.5%.
  • mandelbrot_chunked: a single launch.
  • super_light: 0.29 ms per launch (116 ms / 400), so 8 thread creations (about 0.15 ms) are half the launch.

Little or no work for some workers. In spin_between_run_calls, the middle launch has 2 tasks, so p − 2 workers have nothing to do. Up to p = 8, Spin matches Sleep (about 280 ms). At p = 16, Spin takes 592.9 ms against 280.2 ms for Sleep.

The idle workers each execute the has_work_ load-and-branch loop non-stop, and the calling thread spins on tasks_done_. At p = 16 that is 17 runnable threads on 16 hardware threads. The two workers computing fib(40) must share their cores with spinning SMT siblings and are time-sliced against the extra thread, so the useful work takes twice as long. The answers stay correct, but the spinners occupy hardware threads, take execution slots from their SMT siblings, keep the cores out of idle power states, and steal CPU from any other program.

The same effect wrecks Spin on every many-launch workload at p = 16. super_super_light goes from 12.9 ms at p = 8 to 259.7 ms at p = 16, and ping_pong_equal from 269 to 475 ms. When a worker holding a task is descheduled, everyone waits for it.

Faster than Spawn, yet efficiency still falls. On super_light, Spin is faster than Spawn at every p ≤ 8, but its efficiency still falls: E = 0.95, 0.87, 0.66 at p = 2, 4, 8 (Spawn: 0.72, 0.50, 0.17). Both are true because the pool removes only one overhead term, thread creation. Each launch still pays costs that do not shrink with p:

  • publishing the launch and waiting for the slowest task (the barrier),
  • contention on the claim mutex, which grows with p,
  • a tail of 64 tasks spread over p workers.

Meanwhile the useful work per worker shrinks as 1/p. An overhead that stays constant while the work divides makes Tp fall more slowly than 1/p, so Ep = T1/(p·Tp) declines even though the pool beats Spawn at every p.

Separating thread management from useful computation. I take useful computation per worker as T1/p and overhead as Op = Tp − T1/p. For super_light at p = 8:

  • Useful work: 14.5 ms.
  • Spawn overhead: 69.2 ms. Spin overhead: 7.4 ms.
  • The difference, 61.8 ms over 400 launches, is 155 µs per launch, i.e. about 19 µs to create and join each of the 8 threads. That is the thread-management cost.
  • The 7.4 ms Spin still pays (about 18 µs per launch) is synchronization, claiming and end-of-launch imbalance.

The same calculation gives 72–76 µs per launch at p = 1–2 and 113–231 µs at p = 8–16 for math_operations_in_tight_for_loop. Limitations:

  • T1/p assumes the parallel work costs the same as the serial work. Cache effects break this: the reduction tree runs 1% faster than T1 at p = 1, so Op is uncertain by about ±1% of T1.
  • End-to-end timings cannot separate synchronization from load imbalance.
  • Pool creation is outside the timed region, so the pool's own start-up cost is not included.
  • A minimum of 5 runs hides run-to-run variance.
  • The method fails at p = 16 for Spin, whose overhead is dominated by oversubscription; there the Spawn − Spin difference becomes negative.

5. Part 3 — Sleeping thread pool and synchronization

5.1 Synchronization reasoning

When a worker sleeps, and what wakes it. A worker sleeps on work_cv_ while !shutdown_ && next_task_ >= num_total_tasks_, i.e. while the current launch has no unclaimed task. Two events can make the condition true:

  • run() publishes a new launch (next_task_ = 0, num_total_tasks_ = n > 0).
  • The destructor sets shutdown_.

Both happen while holding mutex_, and both are followed by work_cv_.notify_all(). Finishing a task can never make the condition true, so completions do not wake sleeping workers.

What the calling thread waits for. run() sleeps on done_cv_ while tasks_done_ != num_total_tasks_. Whichever worker raises tasks_done_ to num_total_tasks_, i.e. the last task to finish (not necessarily task n−1), calls done_cv_.notify_one(). For n = 0 the condition already holds and run() returns immediately.

An incorrect interleaving. Suppose completion were tracked at claim time, i.e. run() waited for next_task_ == n or a worker incremented tasks_done_ before calling runTask:

  1. Worker W1 claims the last task n−1 (next_task_ becomes n) and releases the mutex.
  2. The caller wakes, sees the launch “complete”, and returns from run(), even though task n−1 has not started.
  3. The test checks its output (task n−1's elements are missing), or the program calls run() again, which resets the counters.
  4. W1 now executes task n−1 of the old launch, after run() has already returned. Its results arrive too late. If it then updates the shared completion counter, that update counts toward the new launch, so the next run() can return one task early too.

My implementation increments tasks_done_ only after runTask() returns, and under the mutex. So tasks_done_ == n implies that every task has returned.

Why the condition is checked in a loop. wait(lock, pred) is while (!pred()) wait(lock);. The loop is required for four reasons:

  1. Spurious wakeups are permitted.
  2. notify_all() wakes every sleeping worker, but a launch with fewer tasks than workers leaves most of them nothing to do. In spin_between_run_calls, 16 workers wake for a 1-task launch; 15 must re-check and go back to sleep.
  3. Between the notify and re-acquiring the mutex, another thread may already have claimed the last task.
  4. If the condition is already true, the thread must not wait at all. The predicate is checked under the mutex before sleeping, so a notification sent before the wait cannot be lost.

5.2 Spawn vs Spin vs Sleep (measured)

Fine-grained workload. On super_super_light with p = 2–8, Spin is fastest: 10.3, 10.2 and 12.9 ms, against Sleep's 13.6, 13.6 and 17.7 ms. Over 400 launches, Sleep's 3.3–4.8 ms extra is 8–12 µs per launch, the price of putting threads to sleep and waking them. Each launch has to wake every worker (a futex system call per thread, plus the time for the scheduler to run it), and when the last task finishes, the caller must also be woken. A spinning worker notices the new launch within about 100 ns. On math_operations_in_tight_for_loop (2000 launches of 16 tasks) the two are within 1–5% for p ≤ 8.

Workload with idle gaps. In spin_between_run_calls, most workers have nothing to do during the 2-task launch. At p = 16, Sleep (280.2 ms) is 2.1× faster than Spin (592.9 ms), because sleeping workers leave the cores to the two threads doing real work. The same holds whenever p reaches the hardware-thread count. At p = 16, Sleep beats Spin on every workload, for example super_super_light 24.0 vs 259.7 ms and math_operations_in_tight_for_loop 214.8 vs 473.8 ms.

Why neither is fastest everywhere. Spinning trades CPU time for reaction time: it wins when launches are short and back to back and every spinner has a hardware thread to itself. Sleeping trades a few microseconds of wake-up latency per launch for zero cost while idle: it wins when workers are idle for long stretches, when there are more runnable threads than hardware threads, and when SMT siblings need the core. Neither cost dominates in all cases, so the faster implementation depends on the workload.

6.3 Granularity experiment

The fine-grained workload has N = 218 items costing 0.1 µs or 1 µs. Its measured serial time is T1 = 158.6 ms, so T ≈ 605 ns of useful work per item on average; the extra over the nominal 550 ns is the timer loop itself. The experiment uses five chunk sizes, from 1 item per task (262144 tasks) to 65536 items per task (4 tasks).

A chunk size that reduces scheduling overhead: 16, and beyond it 256. At p = 4, chunk 1 costs 90.0 ms (Spin) and 80.2 ms (Sleep), more than twice the ideal 39.6 ms. Every item pays a mutex round trip. Chunk 16 divides the number of claims by 16 and brings both pools to 42.6–42.8 ms. Chunks 256 and 4096 reach 39.4–40.2 ms, within 1.5% of ideal.

A chunk size that worsens load balance and reduces concurrency: 65536 = N/4. There are now only 4 tasks. At p = 4, two tasks hold all the 1 µs items. Each takes about 69 ms, so the makespan is 69.3 ms: 1.75× the best chunk size, and exactly the static contiguous imbalance from Section 6.1, scaled up. At p = 16, the same 4 tasks leave 12 of the 16 workers with nothing to do, and the time stays at 69.5 ms against an ideal of 9.9 ms.

At p = 16, even the best chunk (12.7 ms) is 1.3× the ideal. Two workers on one core slow each other's busy-wait loop, which itself performs work (reading the timer).

Why very fine granularity destroys dynamic scheduling: H/T. With c items per scheduled unit, a worker spends c·T on useful work and H on scheduling for each unit, so efficiency is at most cT/(cT + H) = 1/(1 + H/(cT)).

From the chunk-1 and chunk-256 runs, I estimate H = (Tp(1) − Tp(256))·p/N:

  • Spawn (an atomic fetch_add): 169 ns at p = 4, 391 ns at p = 16.
  • Spin and Sleep (a mutex round trip): 764 and 609 ns at p = 4; 6.2 and 5.2 µs at p = 16.

For the pools at p = 4, H/T ≈ 1.0–1.3, so at least half of every worker's time is scheduling. At p = 16, H/T ≈ 9. H grows with p because every claim goes through the same mutex: claims are serialized, so the pool cannot hand out more than about 3 million tasks per second (262144 claims in roughly 80–100 ms), no matter how many workers wait.

Dynamic scheduling only pays off while H/T is small: its balance benefit is at most one unit's cost at the end of the launch, but its overhead is paid on every unit. Chunking divides the overhead per item by c (H/(16T) ≈ 0.08 at p = 4), and up to about 4096 items per task there are still enough tasks to balance the load. The cheaper atomic claim in Spawn keeps H/T at about 0.3 at p = 4, which is why Spawn is the fastest at chunk 1 (50.9 ms).

7. Part 5 — Asynchronous task graphs with dependencies

7.1 Implementation (part5_async_deps/tasksys.cpp, sleeping pool)

struct Launch { IRunnable* runnable; int num_total_tasks, next_task, tasks_done, unmet_deps;
                std::vector<TaskID> dependents; };            // launches waiting for this one
std::unordered_map<TaskID, Launch> launches_;   // unfinished launches only
std::deque<TaskID> ready_;                      // deps satisfied, tasks left to hand out
// one mutex_ guards everything; work_cv_ wakes workers, done_cv_ wakes sync()
  • runAsyncWithDeps, all under the mutex. It gives the launch the next id (0, 1, 2, …, so ids are unique). For every dependency still in launches_, it appends the new id to that dependency's dependents and increments unmet_deps; a dependency that is no longer in the table has already finished. If unmet_deps == 0, the launch goes into ready_ and notify_all() wakes the workers. It then returns without waiting.
  • Worker. It sleeps until ready_ is non-empty, then claims the next task of the launch at the front. When the last task of that launch has been claimed, the launch leaves ready_, so other workers move on to the next ready launch while its stragglers finish. Independent ready launches therefore run concurrently. After runTask returns, the worker relocks and increments tasks_done. If that was the last task, it calls launchFinished(id).
  • launchFinished removes the launch from the table and decrements unmet_deps of each dependent. Dependents that reach 0 enter ready_ (with notify_all). If the table is now empty, it calls done_cv_.notify_all().
  • The other methods. sync() waits on done_cv_ until the table is empty. run(r, n) is runAsyncWithDeps(r, n, {}) followed by sync(), so it stays a correct synchronous launch. A launch with 0 tasks is finished as soon as it becomes ready. The destructor calls sync(), then stops and joins the workers.

7.3 Dependency analysis

Ready sets and mandatory orderings. At submission, only A is ready. When the last task of A finishes, B and C become ready at the same instant and may run concurrently: there is no edge between them, and their 8 tasks can share the workers. D becomes ready only when both B and C have finished. The mandatory orderings are A→B, A→C, B→D and C→D (so A→D); B and C are unordered.

Total work.

  • WA = 128 × 1 = 128 ms
  • WB = 2 × 8 = 16 ms
  • WC = 6 × 4 = 24 ms
  • WD = 32 × 2 = 64 ms
  • W = 232 ms in total

Critical-path lower bound. Assumptions:

  • Unlimited workers.
  • Zero launch and scheduling overhead.
  • Every task costs exactly the stated average and runs on a single worker; tasks are not divisible.
  • Tasks within a launch are independent.
  • Dependencies are between whole launches: every task of a dependency must finish before any task of the dependent starts.

Under these assumptions, a launch lasts at least as long as its longest task: A 1 ms, B 8 ms, C 4 ms, D 2 ms. The paths are A→B→D = 1 + 8 + 2 = 11 ms and A→C→D = 1 + 4 + 2 = 7 ms, so the critical path is T∞ = 11 ms (through B). With p workers, Tp ≥ max(T∞, W/p), giving T2 ≥ max(11, 116) = 116 ms and T4 ≥ max(11, 58) = 58 ms.

Schedules for 2 and 4 workers. Figure 7.1 is the greedy schedule my runtime follows: free workers claim the next task, and ready launches are served FIFO (B before C). Both schedules respect the dependencies, since B and C start only after the last A task and D only after the later of B and C. They also respect capacity: at most p tasks run at any time.

  • 2 workers. A takes 0–64 ms (64 tasks each). Then B0 and B1 run on 64–72, C0–C5 three per worker on 72–84, and D 16 tasks each on 84–116. Makespan 116 ms, equal to the bound: utilization 100%.
  • 4 workers. A takes 0–32 ms. W0 and W1 run B0 and B1 on 32–40; W2 and W3 run C0–C3 on 32–40. W0 and W1 then run C4 and C5 on 40–44, while W2 and W3 sit idle for 4 ms because D cannot start before C ends. D runs on 44–60. Makespan 60 ms, against the 58 ms bound: utilization 232/(4×60) = 97%. 58 ms cannot actually be reached: the B/C phase packs tasks of 8, 8, 4, 4, 4, 4, 4 and 4 ms onto 4 workers, and no packing finishes in under 12 ms (an 8 ms task cannot share a worker with a 4 ms one within 10 ms).

Why doubling the workers does not halve the time. The same greedy schedule gives 232, 116, 60, 32 and 20 ms for p = 1, 2, 4, 8 and 16, i.e. ×2.0, ×1.93, ×1.88 and ×1.6 per doubling. Three effects stop the halving:

  1. The B/C phase has only 8 tasks, and two of them last 8 ms. Once p ≥ 8, that phase cannot shrink below 8 ms, whatever p is.
  2. D waits for the slowest of B and C, so workers that finish early idle at the barrier, as W2 and W3 do at p = 4.
  3. No schedule beats the 11 ms critical path; A is the only phase that keeps scaling.

At p = 16, A takes 8 ms, B/C takes 8 ms and D takes 4 ms. The time is now dominated by B's 8 ms tasks, not by the amount of work.

Bookkeeping when the final task of a launch finishes. The worker relocks, raises tasks_done to num_total_tasks, and in launchFinished:

  1. Removes the launch from the unfinished table. From now on it counts as satisfied for any future runAsyncWithDeps.
  2. Walks its dependents list, decrementing each dependent's unmet_deps.
  3. Moves every dependent whose count reaches 0 from blocked to ready (into ready_, with notify_all).
  4. Wakes sync() if no unfinished launch remains.

Only the direct dependents of the finishing launch can change state at that instant, and only those for which it was the last unfinished dependency. Nothing else is scanned. In this graph, A's completion makes both B and C ready. Whichever of B and C finishes first changes nothing (D still has one unmet dependency). The later one makes D ready.

A race that could start a dependent early, and the invariant that prevents it. Suppose a launch were treated as complete when its last task was claimed (next_task == n) rather than when it finished:

  1. W1 claims B's last task.
  2. The runtime marks B complete and releases D.
  3. W2 starts D while B's last task is still running. strict_diamond_deps_async and my abcd_dag_async detect exactly this.

A second variant is check-then-register without the lock. A new launch sees dependency X as unfinished. X then finishes and processes a dependents list that does not yet contain the new launch. The new launch then registers and waits forever.

The invariant: a launch is in ready_, or has any task handed out, only if every launch it depends on has tasks_done == num_total_tasks, i.e. all of its runTask calls have returned. It holds because of three facts:

  1. unmet_deps counts exactly the dependencies that were unfinished at registration, and registration and completion are serialized by the same mutex.
  2. unmet_deps is decremented only by launchFinished, which runs after the last runTask has returned.
  3. Workers take tasks only from ready_.

7.4 Measured results

With 2–8 workers, the measured makespans are within 0.2 ms of the hand-computed schedules: 116.2 ms at p = 2 against the bound of 116, 60.1 ms at p = 4, and 32.1 ms at p = 8. Doubling p from 2 to 4 gives 1.93×, not 2×, exactly as the barrier analysis predicts. At p = 16, every hardware thread runs a busy-waiting worker, so any operating-system activity preempts one of them. Both variants come out about 3 ms above the schedule there (23.1 vs 20 ms and 18.7 vs 16 ms).

Splitting the long launch B into four independent sub-launches. Splitting B into B1–B4 (2 tasks × 2 ms each) shortens the critical path from 11 ms (A→B→D) to 7 ms (A→C→D, with C now the longest), and adds 6 more tasks that can run at the same time.

  • p = 2 and p = 4: no gain. Measured 116.2 vs 116.2 ms and 60.2 vs 60.1 ms. With 2 workers the time is set by the total work (232/2 = 116 ms), so extra parallelism cannot help. With 4 workers the ready queue is FIFO, so the eight 2 ms B tasks run first and C's 4 ms tasks form the tail (B tasks on 32–36 ms, C on 36–44 ms). The B/C phase still lasts 12 ms. Running the long tasks first would finish it in 10 ms (58 ms in total), so the benefit also depends on the scheduler's order.
  • p = 8 and p = 16: it helps. 32.1 → 30.1 ms and 23.1 → 18.7 ms, because the B/C phase is no longer limited by B's 8 ms tasks.

The extra launches are not free. Each one costs a hash-table entry, a dependency edge (D now has 5 dependencies instead of 2), a pass through launchFinished and a wake-up of the workers: roughly 10–40 µs each. super_super_light_async runs 400 launches of tiny tasks in about 17 ms, i.e. about 40 µs per launch including its 64 tasks. Against millisecond tasks this is negligible, but if B's tasks took a few microseconds, three extra launches would cost more than the parallelism saves. So extra concurrency helps only when there are idle workers to use it, when the scheduler orders the work well, and when task cost far exceeds launch cost.

Independent launches run concurrently. The table below submits the same bulk launches with run() (one launch at a time) and with runAsyncWithDeps() followed by a single sync().

…_fewer_tasks has only 9 tasks per launch. With run(), at most 9 of the 16 workers are busy and every launch ends at a barrier. Submitted asynchronously, the 2000 launches have no dependencies, so free workers take tasks from the next ready launch while the current one finishes: 282.7 → 121.6 ms at p = 16 (2.3×). …_fan_in gains 1.2× at p = 16. Its 256 math launches overlap, but the final reduce depends on all of them, so the critical path still ends with one serial task.

At p = 1, the synchronous column pays two sleep/wake round trips per launch: the single worker and the waiting caller each sleep and are woken, and each of the 2000 launches incurs this. Most of the p = 1 difference comes from that.

8.2 Predictions: confirmed and contradicted

Confirmed. super_super_light scaled worst: Spawn is slower than serial at every p (S = 0.07–0.47). Also as predicted:

  • The spinning pool beat Spawn most on many-launch workloads (3.8× on super_light at p = 8) and tied on mandelbrot_chunked.
  • Sleep was slower than Spin on super_super_light for p ≤ 8, and 2.1× faster on spin_between_run_calls at p = 16.
  • Part 4: static 20.07 ms vs dynamic 11.06 ms. Chunk 1 was the slowest dynamic setting for the pools (H/T ≈ 1.0–1.3), and chunk 65536 was 1.75× slower than the best chunk size.
  • Part 5: 116.2 / 60.1 / 32.1 ms. Splitting B helped only at p ≥ 8.

Contradicted. I predicted recursive_fibonacci would scale best and gain 10–30% from SMT at p = 16. It gained nothing (7.61 → 7.64 for Spawn). mandelbrot_chunked scaled best: 7.94 at p = 8 and 14.2–14.6 at p = 16, i.e. SMT nearly doubled its speed.

The difference is how fully one thread uses a core:

  • Mandelbrot. The inner loop is a chain of dependent floating-point multiplies and adds. Each operation waits about 4 cycles for the previous result, so one thread leaves most of the core's issue slots empty, and an SMT sibling fills them almost for free.
  • fib(25). It is call- and branch-heavy integer code with short dependencies, so one thread already keeps the core's front end and integer units busy. A sibling only splits the same resources.

I had treated "compute-bound" as one category; SMT gains depend on how much idle capacity each core has. My ping_pong prediction was also too pessimistic. It reached S8 ≈ 7, not saturation at 4–8, because the 4 MB of arrays fit in the 16 MB L3 and each worker's slice stays in its own core's cache.

8.3 When each design is appropriate

  • Spawn suits rare, coarse launches: a few launches of tens of milliseconds, as in mandelbrot_chunked and recursive_fibonacci, where it matched the pools within 1–3%. It also suits code that must not keep idle threads alive between calls, since it is the simplest design with no shutdown logic. Avoid it when launches are frequent or short: it pays about 15–20 µs per thread per launch (S16 = 0.07 on super_super_light).
  • Spinning pool suits frequent, short launches on a machine dedicated to the program, with p no larger than the number of cores, so every spinner has a core to itself. There it has the lowest launch latency (fastest on super_super_light and super_light at p ≤ 8). Avoid it when some workers often have no work, when p reaches the hardware-thread count (from p = 8 to p = 16 it got slower on 10 of the 11 workloads), and on shared or battery-powered machines.
  • Sleeping pool is the general-purpose default. It is within a few percent of Spin when launches are back to back, by far the best at p = 16, robust to idle gaps and to running more threads than cores, and it is the design that extends naturally to asynchronous launches with dependencies (Part 5). Its cost is a wake-up latency of about 10 µs per launch, which matters only when a launch contains a few tens of microseconds of work.
